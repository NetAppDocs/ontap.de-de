= Ein Volume auf eine FabricPool aktivierte ONTAP lokale Ebene verschieben
:allow-uri-read: 
:icons: font
:imagesdir: ../media/


[role="lead"]
Ein link:../volumes/move-volume-task.html["Volume verschieben"] verschiebt ein Volume unterbrechungsfrei von einer lokalen ONTAP Ebene (Quelle) auf eine andere (Ziel), meist für das Hardware-Lifecycle-Management, die Cluster-Erweiterung oder den Lastausgleich. Wird ein Volume auf eine für FabricPool aktivierte lokale Ebene verschoben, hilft das Verständnis der Auswirkungen der Verschiebung auf ausgelagerte Daten und Tiering-Richtlinien, unnötigen Netzwerkverkehr und Objektspeicherkosten zu vermeiden.

Änderungen, die eine Volume-Verschiebung am lokalen Tier, am angehängten Cloud-Tier und an den Volume-Tiering-Richtlinien vornimmt, können erhebliche Auswirkungen auf die Funktionalität von FabricPool haben.


NOTE: Vor ONTAP 9.7 verwendet System Manager den Begriff _aggregate_, um eine _lokale Ebene_ zu beschreiben. Unabhängig von der ONTAP Version verwendet die ONTAP CLI den Begriff _aggregate_. Weitere Informationen zu lokalen Ebenen finden sich unter link:../disks-aggregates/index.html["Festplatten und lokale Ebenen"].



[[destination-local-tier]]
== Ziel-Lokale Tier

Wenn die lokale Ziel-Tier einer Volume Verschiebung keine angebundene Cloud Tier hat, werden Daten auf dem Quell-Volume, die auf der Cloud Tier gespeichert sind, in die lokale Ziel-Tier geschrieben.

Ab ONTAP 9.8 stellt FabricPool, wenn für ein Volume link:determine-data-inactive-reporting-task.html["Meldung inaktiver Daten"] aktiviert ist, anhand der Heatmap des Volumes kalte Daten für das Tiering in die Warteschlange, sobald die Daten auf die lokale Zielebene geschrieben werden.

In ONTAP 9.7 und früheren Versionen setzt das Verschieben eines Volumes auf ein anderes lokales Tier die Inaktivitätsdauer von Blöcken auf dem lokalen Tier zurück. Wenn beispielsweise ein Volume die Auto Volume-Tiering-Richtlinie verwendet und Daten auf dem lokalen Tier enthält, die seit 20 Tagen inaktiv sind, aber noch nicht tiered wurden, setzt das Verschieben eines Volumes die Temperatur dieser Daten auf 0 Tage zurück.



[[optimized-volume-moves]]
== Optimierte Volumenverschiebungen

Ab ONTAP 9.6 werden bei einer Volume-Verschiebung Daten auf dem Quell-Volume, die im Bucket gespeichert sind, nicht zurück in das lokale Tier verschoben, wenn das Ziel-Local-Tier denselben Bucket verwendet wie das Quell-Local-Tier. Tiering-Daten bleiben unverändert, und nur häufig benötigte Daten müssen von einem lokalen Tier in ein anderes verschoben werden. Diese optimierte Volume-Verschiebung führt zu einer deutlich höheren Netzwerkeffizienz.

Beispielsweise löst bei einer optimierten Volume-Verschiebung von 300 TB die Verschiebung von 300 TB kalter Daten von einer lokalen Ebene auf eine andere weder 300 TB an Lesevorgängen noch 300 TB an Schreibvorgängen im Objektspeicher aus.

Nicht optimierte Volume-Verschiebungen erzeugen zusätzlichen Netzwerk- und Rechenverkehr (Lese-/GET- und Schreib-/PUT-Vorgänge), wodurch die Anforderungen an den ONTAP Cluster und den Objektspeicher steigen und beim Tiering auf öffentliche Objektspeicher potenziell höhere Kosten entstehen.

[NOTE]
====
Einige Konfigurationen sind mit optimierten Volumenverschiebungen nicht kompatibel:

* Änderung der Tiering-Richtlinie während einer Volumenverschiebung
* Quell- und Ziel-Lokalschichten verwenden unterschiedliche Verschlüsselungsschlüssel
* FlexClone Volumes
* FlexClone übergeordnete Volumes
* MetroCluster (unterstützt optimierte Volumenverschiebungen in ONTAP 9.8 und höher)
* Nicht synchronisierte FabricPool Mirror Buckets
* Volume wird von einer Plattform, die QuickAssist Technologie (QAT) unterstützt, zu einer Plattform verschoben, die dies nicht unterstützt


Weitere Informationen zu link:https://kb.netapp.com/on-prem/ontap/DP/SnapMirror/SnapMirror-KBs/How_do_platforms_supporting_QAT_or_zlib_compression_impact_SnapMirror_and_volume_move["wie QAT Volume-Verschiebungen beeinflusst"^].

====
Wenn die lokale Ziel-Speicherebene eines verschobenen Volumes über eine zugeordnete Cloud-Speicherebene verfügt, werden die Daten des Quell-Volumes, die auf der Cloud-Speicherebene gespeichert sind, zunächst auf die lokale Speicherebene der lokalen Ziel-Speicherebene geschrieben. Anschließend werden die Daten, sofern die Tiering-Richtlinie des Volumes dies zulässt, auf die Cloud-Speicherebene geschrieben, die der lokalen Ziel-Speicherebene zugeordnet ist.

Das Schreiben von Daten zuerst auf den lokalen Tier verbessert die Performance beim Verschieben eines Volumes und verkürzt die Cutover-Zeit. Wenn Sie beim Verschieben eines Volumes keine Volume-Tiering-Richtlinie festlegen, verwendet das Ziel-Volume die Tiering-Richtlinie des Quell-Volumes.

Wenn Sie beim Verschieben des Volumes eine andere Tiering-Richtlinie festlegen, wird das Zielvolume mit der festgelegten Tiering-Richtlinie erstellt, und die Volume-Verschiebung ist nicht optimiert.



[[volume-metadata]]
=== Volume Metadaten

Unabhängig davon, ob eine Volume Verschiebung optimiert ist, speichert ONTAP eine erhebliche Menge an Metadaten zu allen Daten, sowohl zu lokalen als auch zu per Tiering verschobenen Daten, einschließlich ihres Speicherorts, der Storage Effizienz, der Berechtigungen und der Nutzungsmuster. Metadaten verbleiben immer auf dem lokalen Tier und unterliegen nicht dem Tiering. Wenn ein Volume von einem lokalen Tier auf einen anderen verschoben wird, müssen diese Informationen ebenfalls auf den lokalen Ziel Tier verschoben werden.



[[duration]]
=== Dauer

Volume-Verschiebungen benötigen weiterhin Zeit. Es ist davon auszugehen, dass eine optimierte Volume-Verschiebung ungefähr genauso lange dauert wie die Verschiebung einer gleich großen Menge nicht abgestufter Daten.

Der vom  `volume move show`Befehl gemeldete Durchsatz stellt lokal aktualisierte Volumendaten dar, nicht Daten, die aus dem Cloud-Tier verschoben wurden.


NOTE: Wenn sich Volumes in einer SVM DR Beziehung befinden, müssen Quell- und Ziel-Volumes dieselbe Tiering-Richtlinie verwenden.

.Schritte
. Mit dem  `volume move start` Befehl lässt sich ein Volume von einer lokalen Quellebene auf eine lokale Zielebene verschieben.


.Beispiel für das Verschieben eines Volumens
Im folgenden Beispiel wird ein Volume mit dem Namen `myvol2` der `vs1` SVM auf `dest_FabricPool` verschoben, eine FabricPool-fähige lokale Ebene.

[listing]
----
cluster1::> volume move start -vserver vs1 -volume myvol2
-destination-aggregate dest_FabricPool
----
